# jstack Dashboard Redesign — Design Doc

**Decision needed now: none.** This is a planning artifact, not a proposal with a deadline —
it's a single-user internal tool with no external approver. Phase 1 (real Skills panel + other
read-only views + skill management, on the unchanged backend) is what's being built next; Phase
2 (`AgentTask` unification, ACP provider layer, crew wizard) is FYI-only and not up for sign-off
until Phase 1 has shipped and been used.

Status: **Revised after mockup review — the user clarified jstack is meant to be a "command
center" (interact/setup/manage), not primarily a viewer. Skill management (toggle auto-invoke,
edit skill_defaults) moved from Phase 2 into Phase 1 as a result. This reopens Phase 1's
persona sign-off (previous round assumed a purely read-only P1) — round 4 review pending before
the mockup is finalized.**
Produced via `/brainstorming` with the user, 2026-08-22.

## "Command center" framing (added after mockup review)

The user's request maps mostly onto things already planned, plus two genuinely new write paths:
- **"See arguments needed"** — every skill already has an `argument-hint` frontmatter field.
  Free to surface in P1's Skills panel; no new backend work, no phase change.
- **"Schedule them"** — jstack's existing routine system (`jstack schedule setup/enable/
  disable/run`) already covers this; it's the Tasks panel, still P2 (see below — this specific
  one stays deferred; it's the setup-wizard/to-do/provider-rewrite work that's genuinely new and
  heavier, not skill management).
- **"Enable/disable a skill"** — confirmed to mean toggling whether the model can auto-invoke it
  (the `disable-model-invocation` frontmatter flag), not a UI-only filter.
- **"Customize them"** — editing `skill_defaults.<skill-id>` in config.
- Both of the last two were first placed in Phase 2 (same risk category as the crew-agent
  wizard), then explicitly moved to **Phase 1** after the user clarified that deferring *all*
  management/interaction to "later" undersold the actual point of the product — see Decision Log.

## Phasing (revised twice: round 2 review introduced it, mockup review moved skill management
into P1)

**Phase 1**: redesign the frontend, wire up every read-only visibility panel, **and** ship real
skill management — the first proof this is a control panel, not a catalog. Concretely: Overview
(incl. usage/cost widget, off existing telemetry), **Skills browser with real management** (view
+ argument-hints + toggle `disable-model-invocation` + edit `skill_defaults.<id>`, gated by the
regeneration-safety check below), Crew-agent roster (still view-only — the crew *wizard*, a
bigger new-write-flow, stays P2), Persona-agent roster, Memory browser, Config viewer, Reports
viewer, Settings (theme toggle only — no provider status yet), and the redesigned Agent chat
page (AI Elements UI, still calling today's proven `spawn('claude', ...)` directly — the provider
rewrite is separate from skill management and stays P2). The backend for everything except skill
management is unchanged; skill management is the one deliberate, scoped exception, because it's
what makes Phase 1 actually match "command center" rather than "read-only preview of one."

**Phase 2 (explicitly deferred, not dropped)**: crew-agent setup wizard (new write flow, bigger
than a toggle — creating/editing a whole agent definition), the to-do system (new data model +
local store + concurrency handling), the provider-layer rewrite (ACP/`@simpill/acp-llm-cli` +
the `DASHBOARD_PROVIDER_BACKEND` rollback flag), full Settings (provider status, once the
provider layer exists), and the global floating assistant widget (new persistent UI + a new
security-critical constrained endpoint — deserves its own focused round, not to ride in on Phase
1's redesign).

**Skill management's required safety check (now a Phase 1 requirement, not a deferred one)**:
most `SKILL.md` files are regenerated by `scripts/apply_detailed_skills.py` from data in
`apply_detailed_skills_data.py`, and a hand-or-UI edit to a regenerated file's frontmatter is
silently reverted the next time that script runs, unless the skill is in its `SKIP` set. Before
writing a toggle or a `skill_defaults` edit, the write path must check whether the target skill
is in `SKIP`: if yes, write the file directly; if no, either (a) refuse the write with a clear
"this skill is generated — edit `apply_detailed_skills_data.py` instead" message, or (b) write to
both the file *and* the generator's data source in one transaction. Choosing (a) vs. (b) is now a
Phase 1 design decision — flagging the requirement here so it's designed for before
implementation starts, not discovered mid-build.

The rest of this doc's "Final Design" section describes the complete system (both phases) for
continuity; panel/feature entries below are labeled `[P1]`/`[P2]`.

## Success metric (added after round 1 review — CEO/PM lens: "unfalsifiable impact")

**Usage frequency.** The redesign worked if you actually keep opening the dashboard regularly
(checked informally a month after v1 ships) instead of defaulting back to the CLI for the things
it now covers. If usage frequency doesn't hold up, that's the signal to find out why (wrong
panels, wrong IA, missing the thing you actually needed) rather than a proxy like "feels nicer."

## Understanding Summary

- **What**: A redesigned frontend (new IA, visual design, first-party plugin-panel shell) for
  jstack.core's existing `dashboard/`. The proven backend (claude-cli streaming, auth,
  session-resume, telemetry) stays and gets extended, not replaced.
- **Why**: jstack's state today (skills, agents, memory, config, routines) is scattered across
  CLI commands with no unified view. Goal: one visibility-first home base.
- **Who**: Single user, personal use, reachable on the local network (including phone) — not
  multi-tenant, not internet-exposed.
- **V1 scope**: skills browser, crew-agent roster, persona-agent roster (separate panel), memory
  browser, config viewer, reports viewer, settings (providers + theme), redesigned agent chat,
  crew-agent setup wizard, and task management (routines/workflows view **+** a new lightweight
  to-do layer) — plus a separate global floating "jstack assistant" chat widget scoped to
  jstack-only actions, and a usage/cost widget on the Overview fed by this session's telemetry
  wiring. (Reports, Settings, and the usage widget were caught as gaps during a feature-list
  review after the initial design pass and folded in before persona sign-off.)
- **Multi-provider**: Claude only works at launch. The backend adopts `@simpill/acp-llm-cli`
  (SkinnnyJay, real/maintained/Zod-validated) as a **direct npm dependency** — user's explicit,
  informed choice, knowing it's a small single-maintainer package.
- **Style**: clean/modern/minimal, dark/light, mobile-responsive, shadcn + Vercel AI Elements,
  Zod at every boundary, enums/consts/types over magic strings, KISS.

## Assumptions

- "Plugin architecture" = first-party, statically-registered panels in one shell (no dynamic/3rd-
  party code loading, no sandboxing) — keeps the injection surface small.
- Access stays local-network-only; no new auth model beyond today's single-login/session-cookie.
- Onboarding is folded into the config viewer / a "getting started" section, not a separate panel.

## Unified agent tasks (crew + routines merge — added after live-prototype review)

Replaces this doc's earlier framing of "crew-agent setup wizard" as a standalone Phase 2 feature.
Instead, Phase 2's crew/routines work becomes: design and ship the `AgentTask` config shape
below, a migration off today's separate `crew`/`routines` `jstack.config.json` keys, a CLI surface
(`jstack tasks list/create/edit/run --json`, replacing `crew agents *` and `schedule *`), and the
dashboard management UI for it (the panel this doc previously called "Crew agents" becomes
"Agent tasks").

```ts
type AgentTask = {
  id: string;                    // kebab-case; replaces both crew agent ids and routine ids
  prompt: string;                // freeform instruction — replaces routines' rigid chain-of-skill-ids;
                                  // the model can invoke skills itself from the prompt
  trigger: TaskTrigger;
  durationMs: number;             // max runtime before force-kill (today's RUN_TIMEOUT_MS role)
  priority: "low" | "normal" | "high";
  success?: { kind: "eval" | "script" | "prompt" | "filepath"; ref: string };
  failure?: { kind: "eval" | "script" | "prompt" | "filepath"; ref: string };
  enabled: boolean;
  metadata?: Record<string, string>;  // open-ended, e.g. { owner: "jon", tags: "oncall,daily" }
};

type TaskTrigger =
  | { kind: "cron"; expr: string; metadata?: Record<string, string> }
  | { kind: "interval"; everyMs: number; metadata?: Record<string, string> }
  | { kind: "sigil"; pattern: string; metadata?: Record<string, string> }   // preserves crew's Slack-mention-triggered behavior
  | { kind: "filewatch"; path: string; metadata?: Record<string, string> }  // triggered when a file/glob changes
  | { kind: "manual"; metadata?: Record<string, string> };
```

`success`/`failure` are optional and strictly additive over today's behavior: unset means today's
exact fallback (report "process completed without error," never a real semantic verdict). Set,
`kind: "eval"` runs an a2a-style eval against the run's output, `"script"` runs a deterministic
check, `"prompt"` asks a fresh judge model, `"filepath"` checks whether a file exists (default
assertion for that kind; content/mtime-based variants can layer on later without changing the
shape). This is this doc's answer to a limitation named earlier this session and left
unaddressed: `scheduler.ts`'s own comment states routines deliberately never assert real
success, "which nothing in this repo has a mechanism to verify" — `AgentTask` is that mechanism,
made opt-in so it doesn't force every task to carry a judge call it doesn't need.

**Not yet decided** (flagging now, deciding when this reaches its own design/review pass, not
here): the exact migration path for existing `crew`/`routines` config entries (a one-time
conversion script vs. a compatibility shim); whether `sigil`-triggered tasks still require the
Slack-specific plumbing in `cli/src/lib/crew/slack.ts` verbatim or get re-homed under the new
provider layer; and where `priority` actually gets enforced (a single global task queue vs.
per-trigger-kind queues).

## Final Design

### Architecture
- App shell: one root layout with a slim top bar (search/`Cmd+K`, theme toggle, provider
  indicator), routed page content, and a floating chat widget mounted once at the root.
- Panel registry: each feature area is a module under `src/panels/<name>/` exporting a typed
  `Panel` contract (`id: PanelId` enum, `route`, `summaryCard`, `page`). One line in
  `panels/registry.ts` per panel. This is the "plugin architecture."
- Backend provider layer: `lib/providers/` wraps `@simpill/acp-llm-cli` behind a jstack-owned
  `AgentProvider` interface (enum of supported CLIs). `/api/agent/stream` is rewritten to call
  this instead of `spawn('claude', ...)` directly — same external behavior, CLI-specific logic
  moves behind one seam. Only the Claude enum value has a real implementation at launch.
  **Rollback (added after round 1 review — Engineer/QA lens: "unnamed failure mode," "no
  rollback plan"):** this rewrite touches the only currently-working feature (chat), routing it
  through a 1-star, single-maintainer dependency. Gated behind an env flag,
  `DASHBOARD_PROVIDER_BACKEND=acp|direct` (default `direct` until the ACP path has run in
  production for a real stretch); `direct` keeps the existing, proven `spawn('claude', ...)` path
  verbatim, untouched by the rewrite, as the fallback. If `@simpill/acp-llm-cli` breaks or is
  abandoned, flipping one env var reverts chat to exactly what works today — no redeploy of
  reverted code required.
- Data endpoints: one read-only API route per panel, each backed by shelling out to the existing
  `jstack <cmd> --json` CLI commands — the CLI stays the single source of truth, never
  reimplemented in the web layer.

### Empty / first-run states (added after round 1 review — Designer lens: "no empty state, only
happy path")

Every panel's summary card and full page has an explicit empty state, not a blank render:
- **Crew agents**: P1 (view-only, no wizard yet) — "No agents yet — run `jstack crew agents add`
  to create one" (CLI pointer, matching the wizard's absence in this phase). **P2** (once the
  setup wizard ships): same empty state, but the CLI pointer becomes a button straight into the
  in-app wizard.
- **Tasks / to-dos**: "No to-dos" with the add-task input already visible, not hidden behind
  an extra click.
- **Memory**: "No entries yet" (a real first-run state — a fresh `.jstack/memory.jsonl` is
  genuinely empty, not a fetch failure) — distinct from the discriminated-union `error` state.
- **Reports**: "No reports generated yet" + a pointer to `jstack report render`.
- **Agent chat**: summary card before any session exists shows "No sessions yet — start a chat"
  (not a blank card); the full page's empty state is the existing "No messages yet. Type below
  and send." already proven in the current dashboard.
- **Usage/cost widget**: "No usage recorded yet" with zero-value axes shown (not a hidden/collapsed
  widget) — a real zero is different from a broken widget, and hiding it entirely would make a
  telemetry wiring bug indistinguishable from "just hasn't run yet."
- **Skills / Persona agents / Config**: never genuinely empty (skills/config always exist once
  jstack is installed) — no empty state needed here, only loading/error.

### Accessibility & mobile (added after round 1 review — Designer lens)
- `Cmd+K` palette: full keyboard operability (open/close/arrow-navigate/select), visible focus
  ring, and an on-screen affordance for touch/no-keyboard access (a small search icon in the top
  bar) since "mobile-responsive" was an explicit requirement and phones don't have `Cmd+K`.
- Floating chat widget: proper focus trap while open, `Escape` to close, returns focus to the
  trigger button on close.
- Overview's widget grid: single-column stack on mobile viewports, not a shrunk 3-column grid —
  each summary card is designed to be legible at phone width from the start, not adapted later.

### Concurrency (added after round 1 review — QA lens: no test named for concurrent access)
`.jstack/tasks.json` (and any other new local-file store) is read-modify-written with a simple
file lock (write to a temp file, atomic rename) to avoid two devices/tabs racing a write into
corruption — checked by a test that fires two concurrent writes and asserts neither is lost.

### Data flow
One direction only: browser → Next.js API route → `spawn()` the real `jstack` CLI with `--json`
→ Zod-validate the CLI's JSON output → return to client. No panel talks to jstack internals
directly.

Global chat widget: separate endpoint `/api/assistant/stream` with a hardcoded, non-overridable
read-only tool allowlist — structurally, not just via prompt, so injected content it reads (a
memory entry, a skill body) can't escalate to writes or shell execution.

### Security & error handling
- Every shell-out uses `spawn(cmd, [...args])` array form — never a shell string.
- Zod validates every request body in and every CLI JSON blob out.
- To-do store path-contained under `.jstack/`, same pattern as existing config/telemetry code.
- Auth unchanged: session-cookie + rate-limited login, gating the local-network binding.
- Every data hook returns a discriminated union `{status: "loading"|"error"|"ok", data, error}` —
  no panel treats a fetch failure as an empty state.

### Testing strategy
- Per-panel data hook: unit test against a mocked real CLI-shape response.
- Per API route: request-validation test (bad body → 400) + one live-CLI integration test
  against a temp fixture project (no mocks).
- Panel registry: one integration test asserting every registered panel renders its summary card
  and full page without throwing.
- Provider layer: contract test proving Claude still streams end-to-end through the new seam,
  **plus** a test proving `DASHBOARD_PROVIDER_BACKEND=direct` bypasses the ACP seam entirely and
  reproduces today's exact `spawn('claude', ...)` behavior (the rollback path must be exercised
  by a real test, not just exist in theory).
- Chat widget: test proving its endpoint rejects any tool outside the read-only allowlist, even
  if explicitly requested.
- Local file stores (`tasks.json` and similar): concurrent-write test (two simultaneous writes,
  assert neither is lost) and an empty-file test (assert the correct panel empty state renders,
  not an error state, when the store is genuinely empty).
