# Browser workflows: what works today

Read this before promising anything about a workflow run. The `jstack:workflows-*` skills describe a
richer surface than the CLI currently implements, and the gap is where fabricated results come from.

## Implemented

| Capability | Where | Notes |
|---|---|---|
| Define a flow as JSON | `WorkflowDefinitionSchema`, [`cli/src/types/workflow.ts`](../../cli/src/types/workflow.ts) | `{id, name, start_url, steps[]}`; step `kind` ∈ `goto`, `click`, `fill`, `wait`, `screenshot`, `ai` |
| Save / load / list / delete | `workflow-engine.ts` | Files at `config/workflows/<id>.json` |
| Import / export | `importWorkflowFromFile`, `exportWorkflow` | Import validates against the schema — this is the real lint |
| Preview a saved flow | `jstack workflow` CLI | Restates the definition; see [`output-preview-summary.md`](output-preview-summary.md) |
| Real execution attempt | `runWorkflowViaClaude`, `workflow-engine.ts` | Spawns a nested `claude -p` instructed to drive a real browser via whatever browser-automation MCP (e.g. Playwright MCP) is configured on the host, capturing a screenshot per step under `artifacts/workflows/<id>/` |

## Not implemented / still unverifiable

| Missing | Consequence for what you may claim |
|---|---|
| **A browser-automation MCP is not guaranteed to be configured.** If none is, the spawned agent is instructed to stop and say so — but that's a nested LLM's *self-report*, not a mechanically guaranteed refusal | Never assert a browser rendered anything without checking whether an artifact actually landed under `artifacts/workflows/<id>/` — `hasWorkflowArtifacts` in `workflow-engine.ts` is the deterministic check; the process exiting cleanly is not it |
| **Per-step outcomes** | The executor's `log` is one block of prose from the nested agent, not structured per-step data. You cannot report "step 4 ok" as a distinct fact unless the prose actually names it |
| **Assertions** | No assert kind and no expectation field. `grep -rn assert cli/src/types/workflow.ts cli/src/lib/workflow-engine.ts` → nothing. Express checks as a `wait` on a state-unique selector |
| **`${ENV_VAR}` substitution in this doc's own examples** | The prompt sent to the nested agent instructs it to resolve `env:VAR_NAME` fill values itself at run time; the workflow definition file never contains a resolved value, and neither should a report |
| **Visual diffing** | This directory previously shipped an `output-visual-diff.md` with `before.png`/`after.png` marked "(fake)" and a "login button moved 2px" verdict. No pixel comparison exists anywhere in the codebase. That example was removed rather than kept as aspiration |

## The rule this boundary implies

The repo polices invented metrics everywhere else (`metrics invented → forbidden` in
`report-generator`; "never claim the run passed without an artifact" in the workflow skills). A live test of
`runWorkflowViaClaude` (no browser-automation MCP configured) returned `{"ok": true, "log": ["...no
steps...were executed..."]}` before this was fixed — the nested agent correctly refused in plain English
while the wrapper still reported `ok: true` because the subprocess itself hadn't crashed. That gap is now
closed: `ok` is gated on `hasWorkflowArtifacts` finding a real file under `artifacts/workflows/<id>/`, not on
process exit status alone. So:

> Report what the executor returned, verbatim, then say what it does and does not establish. Cite the real
> artifact path when one exists; if `ok` came back `false`, that already means no artifact was found — don't
> re-litigate it as a maybe.

## Regenerating this directory's example output

[`output-execution-report.md`](output-execution-report.md) should be regenerated by actually running a flow
(with and without a browser-automation MCP configured) and pasting the real result — not hand-written to look
plausible, which is how this directory got into a stale state once already (see git history: the executor
changed out from under these docs and nobody regenerated them). Then revisit `SAFE_PATH` / `VALIDATION` for
the `workflows/*` keys in [`scripts/apply_detailed_skills_data.py`](../../scripts/apply_detailed_skills_data.py)
if the runner/execute skills' guidance needs to change alongside it.
