# Workflow execution report (example output)

This is what running a workflow **actually** returns today. Captured by calling `runWorkflowStub` on
[`input-flow-definition.md`](input-flow-definition.md), not written by hand:

```json
{
  "ok": true,
  "log": [
    "Would run workflow Staging auth smoke starting at ${STAGING_BASE_URL}/login (9 steps)"
  ]
}
```

So the only honest report is:

> **Flow:** `smoke-staging-auth` (9 steps)
> **Result:** `unverified` — no browser ran.
> **Evidence:** none. The executor is `runWorkflowStub`
> ([`cli/src/lib/workflow-engine.ts`](../../cli/src/lib/workflow-engine.ts)), which returns `ok: true`
> unconditionally, emits one log line, and writes no screenshot and no report file.
> **What this does confirm:** the definition loaded and parsed against `WorkflowDefinitionSchema`, and
> it has 9 steps. Nothing about the application under test.

## Why this file is written this way

An earlier version of this example reported **PASS** in bold, a 32s duration, four per-step `ok` marks,
and a `report-2026-04-25T160032Z.json` log file. **None of that is producible.** The stub has no timer,
no per-step results, and writes no file. That example was a template for fabricating a green run — and
`ok: true` coming back from a stub makes the fabrication easy to believe.

Two rules follow, and they are enforced in `jstack:workflows-runner` and `jstack:workflows-execute`:

1. **`ok: true` from the stub is not a pass.** Report `unverified` and name the missing driver.
2. **No artifact, no claim.** Never report a per-step outcome the runner did not emit. Nine steps in the
   definition does not mean nine steps ran.

When a real driver lands, this file should be regenerated by running it — not edited to look plausible.
See [`capability-boundary.md`](capability-boundary.md).
